switch문, 꼭 써야 하나

if-else 체인을 switch로 바꾸면 깔끔해 보이지만, 실제론 break 빼먹기 같은 함정도 같이 따라온다. 언제 쓰고 언제 피하는지.

switch문은 같은 변수를 여러 값이랑 비교할 때 if-else 체인보다 깔끔해 보인다.

switch (status) {
    case 200: handle_ok(); break;
    case 404: handle_not_found(); break;
    case 500: handle_server_error(); break;
    default: handle_unknown();
}

근데 막상 쓰다 보면 함정이 좀 있다.

1. break 빼먹으면 fall-through

C, C++, Java, JavaScript 같은 언어는 break 안 쓰면 다음 case로 흘러들어간다.

switch (x) {
    case 1: do_a();   // break 빼먹음
    case 2: do_b(); break;
}
// x == 1이면 do_a()랑 do_b() 둘 다 실행됨

의도한 fall-through일 수도 있고 (여러 case 같은 동작 처리할 때) 실수일 수도 있다. 코드 읽는 사람이 구분 못 한다는 게 진짜 문제다. 그래서 의도적이면 // fallthrough 주석을 다는 컨벤션이 있다.

2. 비교 가능한 게 제한적

대부분 언어에서 switch는 정수, enum, 문자열 정도만 비교 가능하다. 범위 비교(x > 10)나 복잡한 조건은 못 쓴다. 그런 거 하려면 결국 if-else.

3. 그래도 좋은 점

  • enum이랑 같이 쓰면 컴파일러가 “모든 case 처리했냐” 체크해준다 (-Wswitch-enum)
  • if-else 체인보다 컴파일러가 jump table로 최적화하기 쉬워서 빠를 때가 있음
  • 의도가 명확해진다 — “이 변수의 값에 따라 분기한다”가 한눈에 보임

그래서

  • 분기 조건이 하나의 변수 값일 때 → switch
  • 범위/복합 조건 섞일 때 → if-else
  • enum 다룰 때 → switch가 거의 항상 맞음 (exhaustiveness 체크)
  • 짧은 2~3개 분기면 → if-else가 더 깔끔할 때 많음

Rust나 Kotlin의 match / when처럼 fall-through 없고 expression으로 쓸 수 있는 거면 거의 무조건 쓴다. C 계열 switch는 좀 더 신중하게.
