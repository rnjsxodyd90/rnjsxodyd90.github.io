큰 모델은 어떻게 학습시키는가 — Week 2~4 정리

분산 딥러닝, Flash Attention, Megatron-LM 강의에서 배운 거 정리. 처음엔 다 따로 노는 주제 같았는데 같이 보니까 한 묶음이더라.

요즘 LLM은 파라미터가 수천억 개다. GPU 한 장에 안 들어가는 건 당연하고, 들어간다 쳐도 학습 끝나는 거 보려면 평생 기다려야 한다. 그래서 여러 GPU에 일을 나눠야 되는데, 이 “나눈다”는 게 막상 보면 생각보다 까다롭다.

Week 2~4 동안 분산 학습 관련해서 세 가지 주제를 들었다. 분산 학습 기본기, Flash Attention, Megatron-LM. 처음엔 다 따로 노는 주제 같았는데 정리해보니까 한 묶음이라서 같이 적는다.

1. 왜 분산이 필요한가

Kaplan(2020)의 Neural Scaling Laws 얘기부터. 모델 크기, 데이터, 컴퓨트를 같이 키우면 손실이 power-law로 줄어든다. 셋 다 같이 키워야지 하나만 키우면 효율이 안 난다.

근데 문제는 하드웨어가 이걸 못 따라온다는 거다.

  • Transformer 모델 크기: 2년에 240배
  • GPU 메모리: 2년에 2배
  • 인터커넥트 대역폭: 2년에 1.4배

연산력(FLOPs)은 그래도 빨라지는데 DRAM이랑 인터커넥트가 못 따라온다. 이게 “Memory Wall”이다. 결국 한 GPU에 모델이 안 들어가고, 들어가도 학습이 너무 오래 걸린다. 그래서 GPU 여러 장 묶어서 협력시켜야 한다.

2. SGD 한 줄 복습

g_t = (1/B) Σ_b ∇f_b(w_{t-1})
w_t = w_{t-1} − α_t · g_t

step size를 감쇠시키면 O(1/log t)로, 고정이면 O(1/t) + O(α)로 수렴. 이 정도만 알고 넘어가자.

3. 데이터 병렬 (Data Parallelism)

가장 직관적인 방법이다. 모델은 전부 복제하고, 미니배치만 GPU 수대로 쪼개서 나눠준다. 각 GPU가 자기 데이터로 local gradient 계산하고, 마지막에 다 모아서 평균낸다. 이 “다 모아서 평균낸다”가 All-Reduce.

All-Reduce를 구현하는 세 가지 방법

(a) Single Master 한 GPU를 마스터로 정해서 거기로 다 보낸다. 마스터가 더해서 다시 뿌린다. 단순한데, GPU가 늘면 마스터로 들어오는 트래픽이 폭발한다. 안 쓰는 이유.

(b) Decentralized (마스터 없음) 마스터 없이 각자가 N/P 조각을 다른 모든 GPU에 보낸다. 각자 자기 책임 chunk를 합산해서 다시 다 뿌린다. 각 GPU 트래픽이 2(P−1)N/P로 줄어든다. 근데 fan-in은 여전히 (P−1)이라 한계가 있다.

(c) Ring All-Reduce ← 실제로 가장 많이 씀 GPU들을 ring으로 연결해서, 매 라운드마다 N/P 조각만 옆 GPU로 넘긴다. (P−1) 라운드 reduce-scatter + (P−1) 라운드 all-gather, 합쳐서 2(P−1) 라운드. fan-in이 항상 1이라서 GPU 늘려도 GPU당 트래픽이 거의 안 변한다. 대신 라운드 수가 P에 비례하니까 P가 너무 커지면 latency가 쌓인다.

통신 비용 정리하면:

  • 파라미터 서버: T_comm = α + PNβ
  • Ring All-Reduce: T_comm = 2((P−1)α + ((P−1)/P)·Nβ)

α는 latency, β = 1/bandwidth.

데이터 병렬의 한계

데이터 병렬로 쓸 수 있는 GPU는 batch size B까지가 한계다. 그 이상은 못 쓴다. 그러면 batch를 키우면 되지 않냐 싶은데, 너무 키우면 generalization gap이 생긴다. validation error가 오른다는 얘기. “sharp minima” 가설로 설명한다.

Linear Scaling Rule (lr을 batch에 비례해서 키우기, warmup 필수)로 어느 정도 보완은 되는데 한계가 있다. ResNet-50 + ImageNet 기준, 8k batch까지는 괜찮고 16k 넘어가면 정확도 떨어진다.

비동기 학습 잠깐

워커가 PS에 gradient를 비동기로 push하면 blocking이 없어서 GPU 활용도가 올라간다. 근데 stale gradient 때문에 수렴이 불안정해진다. 지도학습에서는 거의 안 쓰고 synchronous로 갔다. RL에서는 아직 쓴다.

4. 모델 병렬 (Model Parallelism)

데이터 병렬이 한계에 부딪치면 결국 모델 자체를 쪼개야 한다. 두 가지 방식이 있다.

  • Pipeline Parallelism: 레이어를 stage로 쪼개서 GPU 사이에 파이프라인으로 흘림. GPipe가 대표적. 단점은 bubble — 놀고 있는 시간이 생긴다.
  • Tensor Parallelism: 한 레이어 안의 weight를 GPU들이 나눠서 가짐.
  • 3D Parallelism: 위 둘 + 데이터 병렬을 다 합친 거. GPT-3, GPT-4가 이 방식.

Tensor Parallelism 통신 비용 (FC 레이어)

W를 출력 차원으로 P등분해서 각 GPU가 W_p를 가진다고 하자.

  • Forward — activation을 All-Gather 해야 함. 비용 β(P−1)·B·d_i / P
  • Backward 가중치 gradient ∇W_p = ∇Y_p · X^T — 로컬에서 끝남, 통신 없음
  • Backward 입력 gradient ∇X = Σ_p W_p^T · ∇Y_p — All-Reduce 필요. 비용 2β(P−1)·B·d_i / P

Data vs Tensor 비교

  • Data: T ∝ d_i² / P — 가중치 크기에 quadratic
  • Tensor: T ∝ B · d_i / P — 활성화 크기에 linear

FC가 진짜 넓은 경우 (d_i ≫ B) tensor가 훨씬 유리하다. 반대 상황이면 data가 유리하고. 그래서 골라쓰는 거다.

5. 메모리 — 진짜 빡빡함

Mixed precision + Adam, 파라미터 M개 기준 GPU 한 장당:

  • FP16 파라미터: 2M
  • FP16 gradient: 2M
  • FP32 optimizer states (param master + momentum + variance + grad master): 16M
  • 합계 20M bytes / GPU

1B 파라미터면 20GB/GPU. 여기에 activation은 또 따로 든다. 그래서 ZeRO 계열이 나온 거다. optimizer states, gradients, parameters를 복제하지 말고 GPU 간에 partition하자는 아이디어. CPU/NVMe로 offload하는 ZeRO-Infinity, 계산이랑 통신을 prefetching으로 overlap하는 거까지 다 끌어다 쓴다.

1부 핵심만 다시

데이터 병렬은 쉬운데 큰 모델엔 안 맞고 generalization 한계가 있다. Tensor 병렬은 넓은 FC에서 유리하고, pipeline 병렬은 깊은 모델에 유리하다. 실제 LLM 학습은 셋 다 섞고 거기에 ZeRO + mixed precision을 얹는다. 끝.

Flash Attention

1. 배경 — context 길이 폭발

GPT-1이 512, GPT-3이 2K, GPT-4가 128K, Claude가 200K. Context length가 진짜 빠르게 커지고 있다. 근데 attention은 시간/공간 복잡도가 시퀀스 길이 n에 대해 O(n²) 이다. 길어질수록 attention이 병목이 된다.

2. GPU 메모리 계층

종류 용량 대역폭
Registers 64 KB 19 TB/s
SRAM (L1/공유) 20 MB 매우 빠름
HBM (글로벌) 40 GB 1.5 TB/s

가속기가 빨라질수록 메모리가 더 큰 병목이 된다. Flash Attention의 출발점이 “FLOPs 줄이지 말고 HBM 읽기/쓰기 횟수(IO)를 줄이자” 인 이유다.

3. Attention의 비대칭성

표준 attention:

W_{i,j} = exp(Q_i · K_j)
SoftMax(Q_i; K_1,…,K_n) = W_i / Σ_l W_{i,l}
O = SoftMax(Q K^T) V

출력 O_i는 자기 Q_i 하나만 쓰는데, 정규화는 모든 K가 있어야 가능하다. 이 비대칭성 때문에 단순히 쪼개기가 어려운 거다.

4. 그래서 어떻게 하냐면

두 가지 아이디어가 핵심.

  1. SRAM으로 데이터 한 번 가져왔으면 거기서 끝까지 다 처리해버린다 (aggressive fusion).
  2. K, V를 블록 단위로 SRAM에 올리고, 부분 출력 P랑 정규화 합 z를 running aggregate로 들고 다닌다.

블록 한 번 처리할 때 이런 일이 일어난다.

Load(K_t, V_t)
A_t = exp(Q_i · K_t^T)               # attention score
z_t = z_{t-1} + A_t.sum(-1)          # 정규화 running sum 누적
P_t = A_t · V_t / z_t                # 새 부분 출력
P_t = P_t + (z_{t-1} / z_t) · P_{t-1}  # 이전 출력 다시 정규화
Free(K_t, V_t, A_t, ...)

마지막 블록의 P_t가 최종 O_i가 된다. softmax가 부분합으로 정확히 합쳐지는 형태(algebraic aggregation, Jim Gray 1997)라서 이 트릭이 먹힌다.

5. 성능

  • 6~10배 속도 향상
  • 10~20배 메모리 절감 (시퀀스 길수록 효과 더 큼)
  • A100 utilization 최대 72% (PyTorch 표준 15 TFLOPs/s → FlashAttention-2가 16k seq에서 171 TFLOPs/s)
  • 그러면서 근사 없이 정확한 attention. MLPerf 우승자들이 다 쓴다.

6. 결국

가속기 시대엔 FLOPs가 병목이 아니다. 메모리 IO가 병목이다. 블록화 + 융합 + algebraic aggregation으로 메모리 대역폭을 살리는 게 핵심.

Megatron-LM (NVIDIA, 2019)

NVIDIA가 만든 수십억 파라미터 transformer 학습 프레임워크. 핵심은 tensor parallelism을 transformer block 구조에 딱 맞게 깔끔히 구현했다는 거다. Paper, Repo.

1. GEMM 쪼개는 두 가지 방법

Y = X · A를 두 GPU에 쪼갠다고 하자. 두 가지 방법이 있다.

(a) Row Parallel — A를 row-wise로, X를 column-wise로

  • X = [X_1, X_2], A = [A_1; A_2]
  • 각 GPU가 X_i · A_i 계산 → 결과는 부분합. Y = Y_1 + Y_2
  • forward에 All-Reduce 필요

(b) Column Parallel — A를 column-wise로, X는 복제

  • A = [A_1, A_2]
  • 각 GPU가 X · A_i 계산 → Y = [Y_1, Y_2]로 자연스럽게 분할
  • forward엔 통신 없음. backward에만 All-Reduce 필요

2. f, g operator

통신 패턴을 깔끔히 묶은 두 operator.

  • f: forward에 identity, backward에 all-reduce
  • g: forward에 all-reduce, backward에 identity

f랑 g가 서로 conjugate. 분산 transformer 코드 보면 이 두 개가 뼈대다.

3. Transformer block에 어떻게 적용하냐면

MLP block (Y = GeLU(XA), Z = Dropout(Y · B)):

순진하게 row + column로 자르면 GeLU 직전에 동기화 한 번 더 들어가야 한다. “GeLU of sums ≠ sum of GeLUs” 이거 때문에. Megatron은 이렇게 푼다.

  • 첫 GEMM은 column-parallel — A = [A_1, A_2]
  • GeLU는 element-wise라서 분할된 채로 그냥 통과시킴
  • 두 번째 GEMM은 row-parallel — B = [B_1; B_2]
  • 마지막에 한 번만 all-reduce

→ MLP block당 forward 1 + backward 1 = 2 all-reduce

Self-attention block:

Multi-head라서 column-parallel이 자연스러움 — head를 GPU에 나눠준다. Q/K/V projection은 column-parallel, 마지막 output projection은 row-parallel.

→ attention block당 2 all-reduce

한 transformer 레이어 전체 = 4 all-reduce (MLP 2 + attention 2).

4. 설계 원칙

  • math-heavy operation을 묶어서 동기화 지점을 최소화
  • pre-existing NCCL / PyTorch primitive만 사용 — native PyTorch로 구현 가능했다는 게 포인트
  • Volta tensor core로 mixed precision

5. 결과 — Weak Scaling

Config Hidden Heads Layers Params MP GPUs MP+DP GPUs
1 1536 16 40 1.2B 1 64
2 1920 20 54 2.5B 2 128
3 2304 24 64 4.2B 4 256
4 3072 32 72 8.3B 8 512
  • Model parallel (1→8 GPU): 100% → 77%
  • Model + Data parallel (64→512 GPU): 96% → 74%
  • baseline 1.2B 모델: 39 TFLOPs/s (이론 peak의 30%)
  • 8.3B 파라미터를 512 GPU로 74% 효율 — 당시 사상 최대 규모 NLP 모델

6. 결국

Transformer GEMM 패턴에 맞춰 column-parallel이랑 row-parallel을 페어로 묶으면, 레이어당 NCCL all-reduce 4번만으로 수십억 파라미터 모델을 native PyTorch에서 학습할 수 있다.

세 강의를 묶으면

  • Week 2~3에서 데이터/모델 병렬이랑 collective 통신(all-reduce, all-gather)의 기초를 배운다. Homework 1, 2가 정확히 이 내용.
  • Megatron-LM은 그 tensor parallelism을 transformer에 실제로 적용한 사례. column/row parallel을 페어로 묶는 게 진짜 깔끔하다.
  • Flash Attention은 같은 transformer를 단일 GPU 안에서 메모리 계층 관점으로 다시 본 거다. 분산이 아니라 IO 최소화가 주제.

결국 요즘 LLM 학습은 Megatron류 tensor 병렬 (GPU 간) + Flash Attention류 IO-aware kernel (GPU 안) + ZeRO류 메모리 관리 이 셋의 합작품이다. 처음엔 따로 노는 주제 같았는데 한 번에 보니까 정말 같은 문제의 다른 면들이더라.
