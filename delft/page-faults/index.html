페이지 폴트가 뭐고 왜 신경써야 하나

페이지 폴트 = 메모리에 접근했는데 그게 물리 메모리에 없을 때 OS가 끼어드는 거. minor면 괜찮은데 major는 진짜 느리다.

OS 수업에서 페이지 폴트 처음 배울 때 “그래서 이게 뭔데” 싶었다. 정리해본다.

가상 메모리 한 줄 복습

프로세스가 보는 메모리 주소는 가상 주소다. 실제 RAM의 물리 주소가 아니다. OS가 페이지 테이블이라는 매핑을 들고 있어서, 프로세스가 어떤 주소에 접근하면 그걸 실제 물리 주소로 번역해준다. (실제론 MMU가 하드웨어로 한다.)

그래서 프로세스가 자기는 4GB짜리 연속된 메모리 갖고 있다고 착각해도, 실제론 RAM 여기저기 흩어져 있거나 일부는 디스크에 있을 수도 있다.

페이지 폴트가 일어나는 순간

프로세스가 어떤 가상 주소에 접근했는데, 그 페이지가 물리 메모리에 없으면 CPU가 trap을 발생시킨다. 이게 페이지 폴트다. OS가 끼어들어서 “야 이거 어떻게 처리할까” 결정한다.

Minor vs Major

페이지 폴트도 종류가 있다.

Minor fault (소프트 폴트) 페이지가 사실 물리 메모리엔 있는데, 이 프로세스의 페이지 테이블에 매핑만 안 돼 있는 경우. 예를 들어:

  • 다른 프로세스랑 공유하는 라이브러리(libc 같은 거)를 처음 접근할 때
  • fork() 후 copy-on-write 페이지를 처음 쓸 때
  • 페이지가 free list에 있다가 재할당되는 경우

OS가 페이지 테이블만 업데이트해주면 끝. 빠르다. 마이크로초 단위.

Major fault (하드 폴트) 페이지가 물리 메모리에 진짜로 없어서 디스크에서 읽어와야 하는 경우. swap에서 가져오거나, mmap한 파일을 처음 읽거나.

이게 느리다. SSD라도 페이지 폴트 한 번에 수십~수백 마이크로초. HDD면 밀리초. 메모리 접근 (나노초)이랑 비교하면 수천~수만 배 차이다.

그래서 왜 신경써야 하나

major fault가 많이 일어나면 프로그램이 갑자기 느려진다. CPU는 노는데 디스크만 돌고 있는 상황. 더 나쁜 경우는 thrashing — 메모리가 모자라서 OS가 페이지를 계속 swap in/out 하느라 진짜 일은 못 하는 상태.

학습 코드에서 데이터셋이 RAM보다 크면 이거 자주 본다. 처음엔 빠르다가 어느 순간 갑자기 느려지는 거.

어떻게 확인하나 (Linux)

# 시스템 전체 폴트 통계
vmstat 1
# si, so 컬럼이 swap in/out — 0보다 크면 major fault 발생 중

# 특정 프로세스의 폴트
ps -o pid,min_flt,maj_flt,cmd -p <pid>

# perf로 세부 추적
perf stat -e page-faults,minor-faults,major-faults ./my_program

min_flt는 누적 minor, maj_flt는 누적 major. 실행하면서 maj_flt가 계속 늘면 swap 들어가고 있다는 신호다.

줄이려면

  • 워킹셋을 물리 메모리 안에 들어가게 줄이거나
  • 메모리 더 사거나
  • mmap으로 파일 다룰 땐 madvise(MADV_SEQUENTIAL) 같은 힌트 주거나
  • mlock으로 중요한 페이지는 swap 못 나가게 고정

대부분은 첫 번째다. 알고리즘이나 데이터 구조에서 메모리 더 적게 쓰게 만드는 게 보통 답이다.
